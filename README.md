# Book Illustration Studio

A small web app that turns a book's text into illustrations by driving the
five-step Gemini pipeline from `Book_illustration.ipynb`: define an art style,
extract the main characters, draw their portraits, pick a chapter, and
illustrate it. Every step is user-triggered and resumable — refresh the page,
sign out, or kill the server mid-step, and the project picks up exactly where
durable state says it is, without repeating a Gemini call.

## Prerequisites

- **Python 3.12+**
- **Node 20+**
- A **Gemini API key** (free tier works) from [https://aistudio.google.com/apikey](https://aistudio.google.com/apikey)
- On **Windows**: Git Bash — `start.sh` and `test.sh` are POSIX `sh` scripts

## Setup

```sh
cp .env.example .env          # then set GEMINI_API_KEY inside it
python -m venv .venv
.venv/bin/pip install -r backend/requirements.txt
npm install --prefix frontend
```

## Run

```sh
./start.sh
```

Backend on `http://127.0.0.1:8000`, frontend on [http://localhost:5173](http://localhost:5173).

## Test

```sh
./test.sh
```

Runs pytest (backend) and vitest (frontend). The suites mock Gemini; no key or
network needed.

### On Windows

`start.sh` and `test.sh` are POSIX `sh`. Run them from **Git Bash** — from
PowerShell or CMD, `./start.sh` just opens the file in an editor. If you would
rather stay in PowerShell or CMD, use the wrappers:

```
.\start.cmd
.\test.cmd
```

They locate Git Bash and hand the script over. They deliberately do not use plain
`bash`, which on most Windows machines resolves to WSL's bash — that sees a
different filesystem and cannot use `.venv\Scripts`.

**Stopping it.** Press Ctrl+C. From CMD you will also get `Terminate batch job
(Y/N)?` — answer `Y`. That prompt is unavoidable in a batch file, and answering
it can kill the shell before any cleanup runs, so `start.sh` shuts down **by
port** rather than by job id and clears both ports again on the next startup.
Nothing is left listening either way.

The port-based approach is not incidental: `npm run dev` spawns vite as a
separate process that outlives the npm wrapper, and under Git Bash the shell's
job ids are MSYS numbers rather than Windows PIDs, so neither `kill` nor
`taskkill` can reach the real process. The listening port is the only handle
that is correct on both platforms.

## Environment variables

| Variable                   | Default                    | Meaning                                                              |
| -------------------------- | -------------------------- | -------------------------------------------------------------------- |
| `GEMINI_API_KEY`         | —                         | Your key. Never committed;`.env` is gitignored.                    |
| `GEMINI_TEXT_MODEL`      | `gemini-3.1-flash-lite`  | Text model.                                                          |
| `GEMINI_IMAGE_MODEL`     | `gemini-2.5-flash-image` | Image model (Nano Banana family).                                    |
| `DATA_DIR`               | `./data`                 | Where`app.db` and per-project artifacts live.                      |
| `USE_FAKE_GEMINI`        | `0`                      | `1` runs the app against the in-repo fake instead of the real API. |
| `GEMINI_TIMEOUT_SECONDS` | `180`                    | Per-request timeout; image calls are the slow ones.                  |

The model IDs are the ones the notebook was run with. Model IDs turn over —
re-check them against AI Studio if a call fails with an unknown-model error.

## Architecture overview

- **FastAPI + SQLite (stdlib driver, WAL) + local filesystem.** Book text and
  images are files under `DATA_DIR`, served through the app's own API with
  ownership checks. No S3, no blob store.
- **One conditional `UPDATE` guards the pipeline.** Starting a step is a single
  SQL statement that only succeeds from the correct predecessor status with no
  step running — that one write enforces step order, single execution (a
  double-click, second tab, or concurrent request loses and gets a 409 carrying
  current state), and orphan takeover after a crash.
- **`server_run_id` detects interruption.** Each server process mints an id and
  stamps it on running steps; a running row stamped by a dead process renders
  as *Interrupted*, and the normal user-triggered Retry recovers it.
- **Steps run in a detached in-process asyncio task.** No queue, no broker, no
  worker process. Handlers are resume-aware: work that already landed (say,
  portrait one) is never regenerated by a retry.
- **REST is the durable interface** (bootstrap and commands); a **WebSocket**
  pushes whole project state after every commit, so two tabs watch one run land
  item by item. The React frontend owns no pipeline state and never advances it
  optimistically — every render comes from server truth.
- **Cost discipline is structural.** The book reaches Gemini once, in step 1
  (the sole exception: rebuilding context after Gemini expires a conversation,
  which only a user-triggered retry performs). The SDK is pinned to one attempt
  per request — no automatic retries anywhere. Caps (2 characters, 1 chapter)
  are enforced server-side by validation, never by silently slicing.

## Why no Docker

The app is two local processes and a SQLite file. A compose file would add a
build step and a volume mount to run what `./start.sh` already runs, so per the
assessment's §5.5 invitation: skipped, deliberately.

## Known limits

- **Single uvicorn worker, required twice over.** Both `server_run_id` orphan
  detection and the in-memory realtime registry assume one process. `start.sh`
  pins `--workers 1`; running more breaks interruption detection and live
  updates.
- **Free-tier interaction retention is 1 day.** A project resumed the next day
  has a dead Gemini conversation: the affected step fails once with a clear
  message, and Retry rebuilds context from persisted state (this is the one
  path that re-uploads the book).
- **No `fsync`.** A power loss can lose the last moments of writes; ordinary
  process crashes are already covered by SQLite's WAL.
- **The provider is intermittently uncooperative, and that is visible.** Two
  behaviours were measured against a real key during UAT and are not defects in
  this app: file-backed calls return `403 permission_denied` on roughly 30% of
  attempts, and the image model sometimes answers an illustration request in
  prose instead of drawing. Both surface as a failed step with a clear message,
  with every earlier result preserved, and clear on **Retry**. Nothing is
  retried automatically — §4.3 forbids retry loops, so the retry is yours to
  make. Expect to click Retry occasionally on the image steps. `TESTING.md`
  records the measurements.

## Two deliberate divergences from `app-demo.html`

- **The book stays readable at every stage.** The demo (line 700) renders the
  book panel only while no style exists yet, which makes the book unreachable
  after step 1 — a demo bug, contradicting the requirement that the book be
  readable at any point. Here the book has a permanent panel.
- **No `localStorage` pipeline store, no 8-second stuck threshold.** The demo
  drives progress with `setTimeout` and localStorage and guesses "stuck" after
  `STALE_RUNNING_MS = 8000`. This app's pipeline state lives on the server, and
  interruption is detected by `server_run_id` identity, not by a timer that
  would misfire on any Gemini call slower than 8 seconds.

## Running against the fake provider

Set `USE_FAKE_GEMINI=1` in `.env` and `./start.sh` — a full five-step
click-through with zero quota, deterministic outputs, and the same
orchestration paths as production.
